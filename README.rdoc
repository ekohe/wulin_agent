= wulin_agent

Conversational AI agent for Wulin Master apps. Exposes grid CRUD and custom
actions as LLM tools (ruby_llm + MCP), gated by wulin_permits.

== Installation

Host apps vendor +wulin_agent+ as a git submodule under
+vendor/gems/wulin_agent+.

=== Add the gem to the host app

From the host Rails application:

  cd /path/to/app

Add the repository as a submodule:

  git submodule add git@gitlab.ekohe.com:ekohe/wulin/wulin_agent.git vendor/gems/wulin_agent

Add the gem to the Gemfile:

  gem "wulin_agent", path: "vendor/gems/wulin_agent"

Install dependencies:

  bundle install

For other developers after cloning the project:

  git submodule update --init vendor/gems/wulin_agent
  bundle install

Do not use +--recursive+ on the host app: +wulin_agent+ has no nested submodules.
Declare +wulin_master+ and +wulin_permits+ at the app level (same as other Wulin gems).

== Integration

=== Install generator

From the host Rails application:

  bin/rails generate wulin_agent:install

The generator automatically:

* creates +config/initializers/wulin_agent.rb+
* adds +wulin_agent.js+ and +wulin_agent.css+ to the asset manifest
* requires the assets in the main application bundles
* adds +#wulin-agent-root+ to +app/views/layouts/application.html.haml+
  (or +application.html.erb+) when available

You should see:

  wulin_agent installed

  Routes: automatic with the gem (/wulin_agent/conversations)

  Next steps:
    rails db/migrate
    rake wulin_permits:load_permission
    export OPENAI_API_KEY=sk-...

No manual mount is required in +routes.rb+. The engine routes are loaded
automatically.

=== Dedicated agent page and main menu

The agent workspace is available at +/wulin_agent+. It fills the content area
while keeping the host application's header and main menu. Direct visits and
Wulin Master's AJAX menu navigation both work; switching between the page and
the toolbar drawer preserves the current conversation.

The toolbar drawer is enabled by default. To link the workspace from your
+ApplicationController+ menu, add an item inside your existing submenu:

  item "Wulin Agent", url: "/wulin_agent", icon: :cognition

For menu-only access, disable the toolbar in +config/initializers/wulin_agent.rb+:

  WulinAgent.setup do |config|
    config.toolbar_enabled = false
  end

The page uses the host's +application+ layout and +/header+ and +/menu+
partials. Access requires a current user and inherits the host controller's
authentication checks.

=== Prerequisites

+wulin_agent+ is a Rails engine for Wulin Master apps. Host apps need:

* +wulin_master+ (required dependency, declared in the gemspec)
* +wulin_permits+ (recommended: LLM tools are gated by grid permissions)
* PostgreSQL (+agent_messages.metadata+ is +jsonb+)

Follow the standard Wulin Master / Wulin Permits setup in your app (migrations,
menus, +rake wulin_permits:load_permission+ after adding grids).

=== Database

Copy engine migrations into the host app (each app gets its own timestamps,
avoiding version collisions with local migrations):

  bin/rails wulin_agent_engine:install:migrations
  bin/rails db:migrate

+rails generate wulin_agent:install+ runs +install:migrations+ automatically.

After upgrading the gem, copy any new migrations and migrate again:

  bin/rails wulin_agent_engine:install:migrations
  bin/rails db:migrate

This creates:

* +agent_conversations+ — chat sessions (+approval_mode+ per conversation)
* +agent_messages+ — user/assistant turns (+metadata+ for tool calls, +rating+)
* +agent_knowledge+ — domain glossary and schema mappings
* +agent_skills+ — reusable playbooks distilled from successful tasks
* +agent_api_tokens+ — bearer tokens for MCP clients
* +agent_approval_grants+ — expiring, single-use approval grants shared by all workers

+agent_conversations+ stores +user_id+ as a plain integer (no foreign key), consistent
with other Wulin apps that use OAuth users without a local +users+ table.

=== Approval persistence

Chat approvals use +WulinAgent::ApprovalGrant+ in the primary database. Grants
survive worker changes and restarts, expire after ten minutes, and are bound to
the requesting user. Only a digest of the random token is stored. Approval and
rejection claim a grant with a conditional database update before proceeding,
so concurrent requests or a failed follow-up model response cannot replay a
write. Inspect the actual record before requesting a new action after a failure.
Grants issued by older releases in process memory cannot be recovered; request
and review a fresh proposal after upgrading.

The engine owns grant storage, expiry, cleanup, and atomic consumption. Hosts
with UUID or tenant-scoped schemas may supply an +ApprovalGrant+ subclass:

  class HostApprovalGrant < WulinAgent::ApprovalGrant
    belongs_to :workspace
    belongs_to :user
    before_validation :assign_workspace, on: :create

    def self.for_user(user_id)
      user = User.find_by(id: user_id, active: true)
      return none unless user

      where(user_id: user.id, workspace_id: user.workspace_id)
    end

    private

    def assign_workspace
      self.workspace ||= user&.workspace
    end
  end

  WulinAgent.setup do |config|
    config.approval_grant_class = "HostApprovalGrant"
  end

Use a class name so Rails reloading resolves the current model. +for_user+ scopes
reads, claims and expired-row cleanup. Host model validations and callbacks
control creation; include active-user and workspace validation when required.
Hosts providing their own schema must retain the grant columns and unique
token-digest index, and use their existing migration strategy rather than
installing a second creation migration for the same table. Expired grants are
pruned in batches of up to 100 when that user requests a new grant. Parameters
are private action data and must not be logged. The legacy +Approvals.reset!+
method is a compatibility no-op; use transactional fixtures for test isolation.

=== Permissions

Load Wulin permissions:

  rake wulin_permits:load_permission

This registers grid/action permissions so LLM tools are exposed only when the
current user has the required permissions.

=== LLM providers and model

The engine configures +ruby_llm+ at boot. Set API keys for the providers you
use (environment variables take precedence over Rails credentials):

  OPENAI_API_KEY=sk-...
  ANTHROPIC_API_KEY=sk-...
  GEMINI_API_KEY=...

Default model when +WULIN_AGENT_MODEL+ is unset: +gpt-4o-mini+ (OpenAI).
Override to switch provider, e.g. Claude or Gemini:

  WULIN_AGENT_MODEL=claude-sonnet-4-6
  WULIN_AGENT_MODEL=gemini-2.0-flash
  WULIN_AGENT_MODEL=gpt-5.6-luna

Optional generation settings (unset by default):

  WULIN_AGENT_TEMPERATURE=0.7
  WULIN_AGENT_THINKING=high

+WULIN_AGENT_TEMPERATURE+ sets sampling temperature when supported by the
model. +WULIN_AGENT_THINKING+ sets reasoning effort for thinking-capable
models (e.g. +none+, +low+, +medium+, +high+ on GPT-5.6 Luna). You can also
set these in +config/initializers/wulin_agent.rb+:

  WulinAgent.setup do |config|
    config.temperature = 0.7
    config.thinking_effort = "high"
  end

Restart the app after changing env vars. Only configure keys for providers you
actually use.

=== Assets

Wulin Agent builds its JavaScript/CSS from source during the host application's
asset precompilation. Node.js and npm are required in the build environment;
locked frontend dependencies are installed with +npm ci+ before the build.
Bundles in +app/assets/builds/+ are not committed.

After installation:

  bin/rails assets:precompile

is enough for production.

In development, build the agent after installing it and after every update
of the gem (+git submodule update+ or +bundle update+):

  bin/rails wulin_agent:assets:build

Until it is built, +bin/rails server+ refuses to start with
+WulinAgent::MissingAssetsError+, since every page loading +application.js+
would fail with +Sprockets::FileNotFound+.

Restart the Rails server after running the generator.

== Agent actions

Grid custom actions (declared with +action+ on a +WulinMaster::Grid+) can be
exposed to the LLM as tools alongside CRUD. Use +agent_action+ to describe how
the agent should call them:

  class PersonGrid < WulinMaster::Grid
    action :greet, icon: :waving_hand, title: "Greet"

    agent_action :greet,
      description: "Say hello to someone by name",
      params: { name: { type: :string, required: false } },
      mutating: true
  end

Only actions backed by a controller method are exposed. UI-only actions (e.g.
+:fullscreen+ with no controller endpoint) are ignored.

The tool name follows:

  <controller>__<action>

Example:

  people__greet

Tools are gated by +wulin_permits+:

  people#greet

+agent_action+ options:

* +description+ — text shown to the LLM (falls back to the grid action title)
* +params+ — JSON schema for arguments (+type+, +required+). When omitted,
  parameters are inferred from the controller method via AST
* +mutating+ — whether the action requires write approval (+true+/+false+).
  Defaults to HTTP method: custom actions use POST and are treated as mutating

At runtime, +ActionInferer+ builds a +ToolSpec+ that dispatches through
+GridDispatcher+ to the grid controller, with the same permissions as the UI.

Most custom actions need no configuration: +ActionInferer+ reads
+params[:...]+ from the controller method via AST. Use +agent_action+ only
for actions the inferer cannot parse, or to override the schema or
description.

=== Scanning custom actions

After install, audit which custom actions are ready for the agent:

  bin/rails wulin_agent:scan

The report classifies each grid custom action:

* +skip+ — UI-only (no controller method)
* +inferred+ — params schema auto-detected from the controller
* +declared+ — explicit +agent_action+ on the grid
* +partial+ — tool exists but schema is empty; needs +agent_action+
* +manual+ — inferer failed; needs +agent_action+

Options:

  VERBOSE=1 bin/rails wulin_agent:scan
  WRITE=1 bin/rails wulin_agent:scan
  FORCE=1 WRITE=1 bin/rails wulin_agent:scan

+WRITE=1+ writes a draft +config/wulin_agent_actions.rb+ for +partial+ and
+manual+ actions only. This file is not loaded at boot — copy the
+agent_action+ blocks into your grid classes, fill in +params:+, then delete
the draft.

== Host tools

Host apps can register their own LLM tools without creating a Wulin grid or
controller action. Use this for domain services (validation, provisioning,
reports, …) that do not map cleanly to CRUD.

Register builders in +config/initializers/wulin_agent.rb+. Each builder is a
lambda +->(user) { [ToolSpec, ...] }+ called when the tool registry is built
for that user:

  WulinAgent.setup do |config|
    config.extra_tool_builders << lambda { |user|
      ThemeConfig::AgentTools.build(user)
    }
  end

Each +ToolSpec+ must set +controller: :host+ so the registry treats it as a
host-app tool (not a grid action). Use a plain tool name (e.g.
+analyze_config_flow+), not +controller__action+.

Example tool class in the host app:

  module ThemeConfig
    class AgentTools
      def self.build(_user = nil)
        [
          WulinAgent::ToolSpec.new(
            name: "analyze_config_flow",
            controller: :host,
            operation: "analyze_config_flow",
            description: "Validate a theme config plan JSON for orphan variables and broken chains.",
            mutating: false,
            permission: nil,
            params_schema: {
              properties: {
                plan: { type: "object", description: "Theme config plan JSON" }
              },
              required: ["plan"]
            },
            callable: ->(params, _user) { ThemeConfig::FlowAnalyzer.call(params["plan"]) }
          )
        ]
      end
    end
  end

Visibility and approval:

* +mutating: false+ — read-only host tools are available like +knowledge_search+
  (no grid permission required; any user who can use the agent sees them)
* +mutating: true+ — write host tools follow the same approval rules as grid
  writes (+confirm_writes+ in chat; auto over MCP)

Host tools are included in +WulinAgent::ToolRegistry.for(user)+ alongside grid
CRUD, custom actions, knowledge, skills, and charts. They appear in the in-app
chat agent and on the MCP endpoint (+/wulin_agent/mcp+) for the same user.

== Routes

The engine exposes its routes automatically.

Available endpoint:

  /wulin_agent/conversations

No manual configuration is required in the host application's
+config/routes.rb+.

== MCP server

The engine also exposes its tools through the
{Model Context Protocol}[https://modelcontextprotocol.io] so external clients
(Cursor, Claude Desktop, …) can call the same grid CRUD, custom actions, host
tools, knowledge, and skill tools as the in-app agent.

=== Endpoint

  /wulin_agent/mcp

It speaks the streamable HTTP transport (stateless) and accepts +POST+ and
+DELETE+. The exposed tools are exactly +WulinAgent::ToolRegistry.for(user)+ for
the authenticated token's user, so the same +wulin_permits+ gating applies: a
client only sees the tools that user is allowed to run.

Mutating tools are annotated (+destructive_hint+) and run in +:auto+ approval
mode — there is no interactive confirmation step over MCP, so only hand out
tokens to trusted users/clients.

== Knowledge

Domain terms (acronyms, schema mappings, workflows) live in +agent_knowledge+.

* Global +acronym+ entries (no +scope+, up to 30) are injected into the agent
  system prompt so common terms (NHK, MRL, …) work without a tool call.
* Everything else is fetched on demand via +knowledge_search+.
* The agent can add or remove entries with +knowledge_upsert+ / +knowledge_delete+
  (writes require approval in +confirm_writes+ mode).

Categories: +acronym+, +schema+, +goal+, +glossary+. Optional +scope+ limits an
entry to a grid context (e.g. +orders+). Only global acronyms are injected;
scoped or non-acronym entries stay in the DB.

Tools:

* +knowledge_search+ — read-only; search by query, category, and/or scope
* +knowledge_upsert+ — create or update an entry (mutating)
* +knowledge_delete+ — remove an entry by key (mutating)

Seed common acronyms after migrate:

  WulinAgent::Knowledge.create!(
    key: "NHK",
    value: "Customer — Nippon Hoso Kyokai",
    category: "acronym"
  )

Knowledge tools are available to any authenticated agent user (not gated by
grid permissions). Mutating calls still go through the approval flow.

== Skills

Reusable playbooks live in +agent_skills+. A skill is a named workflow the agent
can follow on demand: a short description (advertised in the system prompt) and
full markdown instructions (loaded when needed).

Each skill stores:

* +name+ — unique identifier (snake_case)
* +description+ — one-line summary shown in the system prompt (up to 30 skills)
* +instructions+ — markdown playbook the agent follows after +skill_read+
* +tool_sequence+ — optional JSON array of +{tool, params}+ steps from a past run
* +usage_count+ — incremented each time +skill_read+ is called
* +created_by+ — user id when created via the UI or +skill_create+

Tools:

* +skill_list+ — read-only; list available skills
* +skill_read+ — read-only; load a skill's full instructions by name
* +skill_create+ — create a skill (mutating; requires approval in +confirm_writes+)
* +skill_update+ — update an existing skill (mutating)
* +skill_delete+ — delete a skill by name (mutating)

Skill names and descriptions are injected into the system prompt (like global
acronyms). The agent calls +skill_read+ to load the full instructions before
following a playbook.

=== Self-improvement (thumbs-up)

After a successful assistant reply, the user can rate it with the thumbs-up
button in the chat panel. This triggers +WulinAgent::SkillDistiller+, which:

* extracts successful tool steps from the conversation turn
* sanitizes them into a reusable skeleton (no large plans/prompt bodies or domain-specific filter values)
* asks the LLM for generic instructions and an optional abstract +tool_sequence+
* falls back to the sanitized skeleton when the model omits +tool_sequence+
* creates a new +agent_skills+ row when the answer is reusable

+skill_read+ also sanitizes legacy +tool_sequence+ values before returning them.

A thumbs-down removes any skill linked to that message. Skills can also be
created or edited manually:

  WulinAgent::Skill.create!(
    name: "list_nhk_orders_by_match",
    description: "Show NHK orders grouped by match",
    instructions: <<~MD,
      1. Call knowledge_search if the user mentions domain terms.
      2. Call get_columns on orders.
      3. Call list_records with filters for the NHK customer.
      4. Aggregate by match, then call render_chart.
    MD
    tool_sequence: [
      {"tool" => "list_records", "params" => {"controller" => "orders"}}
    ]
  )

Skill tools are available to any authenticated agent user (not gated by grid
permissions). Mutating calls still go through the approval flow.

=== Tokens

MCP requests authenticate with a bearer token (+WulinAgent::ApiToken+) instead of a
session. The *MCP tokens* button in the agent header opens a personal token
manager on both the full page and the drawer. Users can list their active tokens,
create a named token (30-day expiry by default), copy the value at creation, and
revoke access. Token values are omitted from list responses and cleared when the
popup closes. Management requires session authentication and CSRF protection.
For hosts with workspace-scoped tokens, management also scopes by workspace.

Tokens can also be managed with the rake tasks:

  # Create a token for a user (printed once, copy it now)
  rake 'wulin_agent:token:create[user@example.com,Cursor]'

  # List tokens (optionally for one user)
  rake 'wulin_agent:token:list'
  rake 'wulin_agent:token:list[user@example.com]'

  # Revoke a token by id
  rake 'wulin_agent:token:revoke[12]'

Tokens can also carry an +expires_at+; the +active+ scope ignores revoked or
expired tokens. Each successful request bumps +last_used_at+.

=== Client configuration

The engine requires MCP 1.7 or later within the 1.x series for this transport
configuration. Update the host's bundle when upgrading the engine.

For a deployed endpoint, configure its hostname in the host application's
+config/initializers/wulin_agent.rb+:

  WulinAgent.setup do |config|
    config.mcp_allowed_hosts = ["your-app.example.com"]
  end

The MCP transport accepts only loopback hosts by default. Entries may be bare
hostnames (any port) or +hostname:port+. Unlisted hosts return +403 Invalid Host
header+. DNS rebinding protection stays enabled: browser requests with an
+Origin+ header must be same-origin; non-browser clients may omit it. Do not
derive the allowlist from request headers.

Point the MCP client at the host app's endpoint and pass the token in the
+Authorization+ header. Example +mcp.json+ (Cursor):

  {
    "mcpServers": {
      "wulin_agent": {
        "url": "https://your-app.example.com/wulin_agent/mcp",
        "headers": {
          "Authorization": "Bearer <token>"
        }
      }
    }
  }

Quick smoke test with +curl+ (JSON-RPC +tools/list+):

  curl -sS https://your-app.example.com/wulin_agent/mcp \
    -H "Authorization: Bearer <token>" \
    -H "Content-Type: application/json" \
    -H "Accept: application/json, text/event-stream" \
    -d '{"jsonrpc":"2.0","id":1,"method":"tools/list"}'

A missing or invalid token returns +401 Unauthorized+.

== Development

=== GitLab CI access to private dependencies

In both +ekohe/wulin/wulin_master+ and +ekohe/wulin/wulin_permits+, go to
+Settings > CI/CD > Job token permissions+ and add +ekohe/wulin/wulin_agent+
to the CI/CD job token allowlist. The user triggering the pipeline must also
have permission to read both dependency repositories.

CI rewrites the Gemfile's SSH URLs to HTTPS using GitLab's automatically
provided +CI_JOB_TOKEN+. No SSH deploy key or manually created token variable
is required. Authentication configuration is passed through the job environment
and is not written to the cached Git repositories. Local development continues
to use the SSH URLs in the Gemfile and lockfile.

=== Local development

Install gems (+wulin_master+ and +wulin_permits+ are fetched from GitLab via the Gemfile):

  bundle install

Build frontend assets:

  cd app
  npm ci
  npm run build

Run tests:

  bundle exec rspec

Host apps vendor Wulin gems at the top level (+vendor/gems/wulin_master+,
+vendor/gems/wulin_permits+, etc.). This repo's Gemfile pulls them from GitLab
for local development and CI only.
