= wulin_agent

Conversational AI agent for Wulin Master apps. Exposes grid CRUD and custom
actions as LLM tools (ruby_llm + MCP), gated by wulin_permits.

== Installation

Host apps vendor +wulin_agent+ as a git submodule under
+vendor/gems/wulin_agent+.

=== Add the gem to the host app

From the host Rails application:

  cd /path/to/app

Add the repository as a submodule:

  git submodule add git@gitlab.ekohe.com:ekohe/wulin/wulin_agent.git vendor/gems/wulin_agent

Add the gem to the Gemfile:

  gem "wulin_agent", path: "vendor/gems/wulin_agent"

Install dependencies:

  bundle install

For other developers after cloning the project:

  git submodule update --init --recursive
  bundle install

== Integration

=== Install generator

From the host Rails application:

  bin/rails generate wulin_agent:install

The generator automatically:

* creates +config/initializers/wulin_agent.rb+
* adds +wulin_agent.js+ and +wulin_agent.css+ to the asset manifest
* requires the assets in the main application bundles
* adds +#wulin-agent-root+ to +app/views/layouts/application.html.haml+
  (or +application.html.erb+) when available

You should see:

  wulin_agent installed

  Routes: automatic with the gem (/wulin_agent/conversations)

  Next steps:
    rails db/migrate
    rake wulin_permits:load_permission
    export OPENAI_API_KEY=sk-...

No manual mount is required in +routes.rb+. The engine routes are loaded
automatically.

=== Prerequisites

+wulin_agent+ is a Rails engine for Wulin Master apps. Host apps need:

* +wulin_master+ (required dependency, declared in the gemspec)
* +wulin_permits+ (recommended: LLM tools are gated by grid permissions)
* PostgreSQL (+agent_messages.metadata+ is +jsonb+)

Follow the standard Wulin Master / Wulin Permits setup in your app (migrations,
menus, +rake wulin_permits:load_permission+ after adding grids).

=== Database

Run the engine migrations:

  bin/rails db:migrate

This creates:

* +agent_conversations+ — chat sessions (+approval_mode+ per conversation)
* +agent_messages+ — user/assistant turns (+metadata+ for tool calls, +rating+)
* +agent_knowledge+ — domain glossary and schema mappings
* +agent_skills+ — reusable playbooks distilled from successful tasks
* +agent_api_tokens+ — bearer tokens for MCP clients

+agent_conversations+ stores +user_id+ as a plain integer (no foreign key), consistent
with other Wulin apps that use OAuth users without a local +users+ table.

=== Permissions

Load Wulin permissions:

  rake wulin_permits:load_permission

This registers grid/action permissions so LLM tools are exposed only when the
current user has the required permissions.

=== LLM providers and model

The engine configures +ruby_llm+ at boot. Set API keys for the providers you
use (environment variables take precedence over Rails credentials):

  OPENAI_API_KEY=sk-...
  ANTHROPIC_API_KEY=sk-...
  GEMINI_API_KEY=...

Default model when +WULIN_AGENT_MODEL+ is unset: +gpt-4o-mini+ (OpenAI).
Override to switch provider, e.g. Claude or Gemini:

  WULIN_AGENT_MODEL=claude-sonnet-4-6
  WULIN_AGENT_MODEL=gemini-2.0-flash

Restart the app after changing env vars. Only configure keys for providers you
actually use.

=== Assets

The JavaScript/CSS assets are already built in the gem
(+app/assets/builds/+).

After installation:

  bin/rails assets:precompile

is enough for production.

In development, restarting the Rails server is usually enough after running
the generator.

== Agent actions

Grid custom actions (declared with +action+ on a +WulinMaster::Grid+) can be
exposed to the LLM as tools alongside CRUD. Use +agent_action+ to describe how
the agent should call them:

  class PersonGrid < WulinMaster::Grid
    action :greet, icon: :waving_hand, title: "Greet"

    agent_action :greet,
      description: "Say hello to someone by name",
      params: { name: { type: :string, required: false } },
      mutating: true
  end

Only actions backed by a controller method are exposed. UI-only actions (e.g.
+:fullscreen+ with no controller endpoint) are ignored.

The tool name follows:

  <controller>__<action>

Example:

  people__greet

Tools are gated by +wulin_permits+:

  people#greet

+agent_action+ options:

* +description+ — text shown to the LLM (falls back to the grid action title)
* +params+ — JSON schema for arguments (+type+, +required+). When omitted,
  parameters are inferred from the controller method via AST
* +mutating+ — whether the action requires write approval (+true+/+false+).
  Defaults to HTTP method: custom actions use POST and are treated as mutating

At runtime, +ActionInferer+ builds a +ToolSpec+ that dispatches through
+GridDispatcher+ to the grid controller, with the same permissions as the UI.

Most custom actions need no configuration: +ActionInferer+ reads
+params[:...]+ from the controller method via AST. Use +agent_action+ only
for actions the inferer cannot parse, or to override the schema or
description.

=== Scanning custom actions

After install, audit which custom actions are ready for the agent:

  bin/rails wulin_agent:scan

The report classifies each grid custom action:

* +skip+ — UI-only (no controller method)
* +inferred+ — params schema auto-detected from the controller
* +declared+ — explicit +agent_action+ on the grid
* +partial+ — tool exists but schema is empty; needs +agent_action+
* +manual+ — inferer failed; needs +agent_action+

Options:

  VERBOSE=1 bin/rails wulin_agent:scan
  WRITE=1 bin/rails wulin_agent:scan
  FORCE=1 WRITE=1 bin/rails wulin_agent:scan

+WRITE=1+ writes a draft +config/wulin_agent_actions.rb+ for +partial+ and
+manual+ actions only. This file is not loaded at boot — copy the
+agent_action+ blocks into your grid classes, fill in +params:+, then delete
the draft.

== Routes

The engine exposes its routes automatically.

Available endpoint:

  /wulin_agent/conversations

No manual configuration is required in the host application's
+config/routes.rb+.

== MCP server

The engine also exposes its tools through the
{Model Context Protocol}[https://modelcontextprotocol.io] so external clients
(Cursor, Claude Desktop, …) can call the same grid CRUD, custom actions,
knowledge, and skill tools as the in-app agent.

=== Endpoint

  /wulin_agent/mcp

It speaks the streamable HTTP transport (stateless) and accepts +POST+ and
+DELETE+. The exposed tools are exactly +WulinAgent::ToolRegistry.for(user)+ for
the authenticated token's user, so the same +wulin_permits+ gating applies: a
client only sees the tools that user is allowed to run.

Mutating tools are annotated (+destructive_hint+) and run in +:auto+ approval
mode — there is no interactive confirmation step over MCP, so only hand out
tokens to trusted users/clients.

== Knowledge

Domain terms (acronyms, schema mappings, workflows) live in +agent_knowledge+.

* Global +acronym+ entries (no +scope+, up to 30) are injected into the agent
  system prompt so common terms (NHK, MRL, …) work without a tool call.
* Everything else is fetched on demand via +knowledge_search+.
* The agent can add or remove entries with +knowledge_upsert+ / +knowledge_delete+
  (writes require approval in +confirm_writes+ mode).

Categories: +acronym+, +schema+, +goal+, +glossary+. Optional +scope+ limits an
entry to a grid context (e.g. +orders+). Only global acronyms are injected;
scoped or non-acronym entries stay in the DB.

Tools:

* +knowledge_search+ — read-only; search by query, category, and/or scope
* +knowledge_upsert+ — create or update an entry (mutating)
* +knowledge_delete+ — remove an entry by key (mutating)

Seed common acronyms after migrate:

  WulinAgent::Knowledge.create!(
    key: "NHK",
    value: "Customer — Nippon Hoso Kyokai",
    category: "acronym"
  )

Knowledge tools are available to any authenticated agent user (not gated by
grid permissions). Mutating calls still go through the approval flow.

== Skills

Reusable playbooks live in +agent_skills+. A skill is a named workflow the agent
can follow on demand: a short description (advertised in the system prompt) and
full markdown instructions (loaded when needed).

Each skill stores:

* +name+ — unique identifier (snake_case)
* +description+ — one-line summary shown in the system prompt (up to 30 skills)
* +instructions+ — markdown playbook the agent follows after +skill_read+
* +tool_sequence+ — optional JSON array of +{tool, params}+ steps from a past run
* +usage_count+ — incremented each time +skill_read+ is called
* +created_by+ — user id when created via the UI or +skill_create+

Tools:

* +skill_list+ — read-only; list available skills
* +skill_read+ — read-only; load a skill's full instructions by name
* +skill_create+ — create a skill (mutating; requires approval in +confirm_writes+)
* +skill_update+ — update an existing skill (mutating)
* +skill_delete+ — delete a skill by name (mutating)

Skill names and descriptions are injected into the system prompt (like global
acronyms). The agent calls +skill_read+ to load the full instructions before
following a playbook.

=== Self-improvement (thumbs-up)

After a successful assistant reply, the user can rate it with the thumbs-up
button in the chat panel. This triggers +WulinAgent::SkillDistiller+, which:

* extracts the tool sequence from the conversation turn
* asks the LLM whether the workflow is worth saving
* creates a new +agent_skills+ row when the answer is reusable

A thumbs-down removes any skill linked to that message. Skills can also be
created or edited manually:

  WulinAgent::Skill.create!(
    name: "list_nhk_orders_by_match",
    description: "Show NHK orders grouped by match",
    instructions: <<~MD,
      1. Call knowledge_search if the user mentions domain terms.
      2. Call get_columns on orders.
      3. Call list_records with filters for the NHK customer.
      4. Aggregate by match, then call render_chart.
    MD
    tool_sequence: [
      {"tool" => "list_records", "params" => {"controller" => "orders"}}
    ]
  )

Skill tools are available to any authenticated agent user (not gated by grid
permissions). Mutating calls still go through the approval flow.

=== Tokens

MCP requests authenticate with a bearer token (+WulinAgent::ApiToken+) instead of a
session. Manage tokens with the rake tasks:

  # Create a token for a user (printed once, copy it now)
  rake 'wulin_agent:token:create[user@example.com,Cursor]'

  # List tokens (optionally for one user)
  rake 'wulin_agent:token:list'
  rake 'wulin_agent:token:list[user@example.com]'

  # Revoke a token by id
  rake 'wulin_agent:token:revoke[12]'

Tokens can also carry an +expires_at+; the +active+ scope ignores revoked or
expired tokens. Each successful request bumps +last_used_at+.

=== Client configuration

Point the MCP client at the host app's endpoint and pass the token in the
+Authorization+ header. Example +mcp.json+ (Cursor):

  {
    "mcpServers": {
      "wulin_agent": {
        "url": "https://your-app.example.com/wulin_agent/mcp",
        "headers": {
          "Authorization": "Bearer <token>"
        }
      }
    }
  }

Quick smoke test with +curl+ (JSON-RPC +tools/list+):

  curl -sS https://your-app.example.com/wulin_agent/mcp \
    -H "Authorization: Bearer <token>" \
    -H "Content-Type: application/json" \
    -H "Accept: application/json, text/event-stream" \
    -d '{"jsonrpc":"2.0","id":1,"method":"tools/list"}'

A missing or invalid token returns +401 Unauthorized+.

== Development

Clone dependencies:

  git submodule update --init --recursive

Install gems:

  bundle install

Build frontend assets:

  cd app
  npm ci
  npm run build

Run tests:

  bundle exec rspec

Wulin gems are vendored as git submodules under +vendor/gems/+ (same layout as
wulintest). +wulin_master+ is a sibling repo on GitLab
(+../wulin_master.git+).
